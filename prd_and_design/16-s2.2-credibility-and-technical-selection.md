# E1-S2.2 可信性分析与关键技术方案选型报告

## 1. 报告定位

本文是 E1-S2.2 的独立决策与上下文恢复报告。即使不读取历史对话，也应能据此理解：

- 为什么 V1.0 从 Hook-first 调整为 OTel + Transcript、OTel-first。
- 哪些结论来自官方契约，哪些来自 Codex 0.154.0 真实样本，哪些是产品决策。
- Session、Turn、本地工具、hosted tools、终态、指标和缺源降级分别能承诺到什么程度。
- 关键技术方案如何比较、为什么选择当前方案、哪些能力被推迟到后续版本。
- 清空上下文后应从哪里继续，哪些工作仍不得提前开始。

报告日期：2026-09-21。

目标生产者版本：`codex-cli 0.154.0`。

当前项目阶段：需求澄清结束前的规格收口。可行性证据和三项人工语义裁决已经完成；在规格一致性检查和 V3 产品/原型设计完成前，不启动正式业务代码迁移。

## 2. 结论摘要

### 2.1 总体可信性结论

V1.0 采用 **OTel + Transcript、OTel-first** 具备可交付可行性，可信度为高，但结论限定于已经验证的产品语义和 Codex 0.154.0 版本契约：

- OTel 是执行发生、事件时间、Trace/Span 父子关系和性能事实的权威来源。
- Transcript 是用户/模型可见内容、工具参数与结果、本地命令状态和原始 JSONL 的权威来源。
- Session、Turn 和 0.154.0 本地模型 Tool Call 均有跨源公共身份，可建立 `EXACT` 关联。
- Turn 可以区分 `SUCCEEDED`、`FAILED`、`INTERRUPTED` 和 `INCOMPLETE`，缺失终态不得合成成功。
- hosted web search 可以执行，但 0.154.0 样本无法提供可交付的单次 hosted tool 身份、状态和耗时，因此该能力移出 V1.0。
- Hook 不进入 V1.0 目标架构，也不作为 OTel 缺失时的兜底；既有 Hook 实现只在迁移完成前用于历史回归和回滚。

### 2.2 已确认的三项产品裁决

用户于 2026-09-21 明确确认：

1. V1.0 不提供 hosted tool 级身份、状态和耗时，只保留其对 Turn 的可观察影响和最终可见内容。完整 hosted tool 生命周期登记为 V1.1 TODO，进入 V1.1 前重新验证目标 Codex 版本契约。
2. OTel 拥有本地工具发生、事件时间、耗时和 trace context；Transcript `CommandExecution.status/exit_code` 拥有本地命令执行结果。Transcript 缺失时结果为 `UNKNOWN`。
3. 一个模型 `custom_tool_call` 包含多个并行 `CommandExecution` 时，建模为一个模型 Tool Call 及其多个子执行。Tool Call 计数为 1，命令执行计数为 N；并行子执行耗时不得求和后作为父 Tool Call 耗时。

## 4. 证据体系与可信性边界

### 4.1 证据等级

| 等级 | 含义 | 允许支持的结论 |
| --- | --- | --- |
| `OFFICIAL` | OpenAI 官方文档明确列出的事件、指标、配置或语义 | 公共契约候选；仍需目标版本适配测试 |
| `VERSIONED_SAMPLE` | Codex 0.154.0 的真实 OTLP/Transcript 脱敏样本 | 锁定 0.154.0 适配行为和回归 fixture；不得无条件外推到其他版本 |
| `SYNTHETIC_FIXTURE` | 仓库内虚构 fixture 或自动测试 | 验证本产品解析、状态和降级规则；不能证明生产者实际发送 |
| `ASSUMED` | 仅由名称、时间接近、二进制字符串或相邻结果推断 | 不得进入正式能力，不得产生 `EXACT` |

打开、渲染和核验具体网页使用 Playwright，并至少检查 HTTP 状态、最终 URL、标题或关键元素。hosted web search 只用于搜索和发现候选网页；搜索摘要不是页面已加载或内容已核验的证据。

原始 OTLP、真实 Transcript、真实 ID、正文、路径、账户和凭据不得进入 Git。仓库中的 `backend/src/test/resources/otel/codex-0.154.0-observed-contract.json` 只保存事件/指标名称和属性键；本地原始样本位于被 `.gitignore` 排除的 `otel-data/`。

### 4.3 不能由当前证据支持的结论

- 不能声称 0.154.0 未观察到的事件在该版本或后续版本中一定不存在。
- 不能把 0.154.0 的字段和值相等关系当作所有 Codex 版本的永久公共契约。
- 不能用 Metric 重建某个具体 Turn、模型请求或工具调用。
- 不能用 OTel `codex.tool_result.success` 判断 shell 命令是否成功退出。
- 不能从 Turn 正常完成反推 hosted tool 的开始、结束、状态或耗时。
- 不能把文件停止增长解释为显式 SessionEnd。

## 5. 已验证事实

### 5.1 Session 与 Turn 身份

- OTel log 的 `conversation.id` 与 Transcript `session_meta.payload.session_id` 同值。
- 同一 Session 下，OTel trace context 的 `turn.id` 与 Transcript Turn ID 同值。
- Session 可用公共 Session ID 精确关联。
- Turn 使用 `(sessionId, turnId)` 作为跨源业务身份；不得假设 `turnId` 脱离 Session 后全局唯一。

可信度：高，`VERSIONED_SAMPLE`。

### 5.2 本地模型 Tool Call 身份

- OTel `codex.tool_decision` 和 `codex.tool_result` 已实际观察。
- 模型级 OTel `call_id` 与 Transcript `custom_tool_call.call_id` 同值。
- Codex 0.154.0 的本地模型 Tool Call 可以建立 `EXACT` 关联。
- `custom_tool_call.call_id` 与子 `CommandExecution.id` 是两个不同身份层级，不能混为同一个业务 ID。

可信度：高，`VERSIONED_SAMPLE`；仅适用于已验证的 0.154.0 本地工具契约。

### 5.3 本地命令结果冲突

真实失败场景中：

- shell 退出码为 `7`。
- Transcript `CommandExecution.status=failed`，且 `exit_code=7`。
- 对应 OTel `codex.tool_result.success=true`。

这不是数据损坏，而是两个字段表达不同语义：OTel `success` 表示工具协议调用产生了结果，不表示该结果中的本地命令退出成功。因此本地命令结果由 Transcript 拥有，OTel 继续拥有调用发生和性能事实。

可信度：高，`VERSIONED_SAMPLE + 用户确认`。

### 5.4 串行、重试与并行层级

- 两次串行调用产生两个模型 Call ID。
- 失败后重试产生两个模型 Call ID，能够表达两次独立尝试。
- 并行场景只产生一个模型 `custom_tool_call`，内部包含两个 `CommandExecution` 子项。

确认后的领域结构：

```text
Turn
└── Model Tool Call (callId)
    ├── Command Execution (executionId, status, exitCode, interval)
    └── Command Execution (executionId, status, exitCode, interval)
```

固定口径：

- 模型 Tool Call 数量按不同模型 Call ID 计数。
- Command Execution 数量按子执行身份计数。
- 并行子执行分别展示状态和时间区间。
- 父 Tool Call 耗时使用整体时间区间或经验证的父 Span，不对子执行耗时求和。
- 失败后重试是多个模型 Tool Call；一次模型调用内并行命令是一个父调用的多个子执行，两者不得混淆。

可信度：高，`VERSIONED_SAMPLE + 用户确认`。

### 5.5 Turn 终态

| 产品状态 | 证据规则 |
| --- | --- |
| `SUCCEEDED` | 成功终止 OTel 证据，并存在正常 Turn 完成证据 |
| `FAILED` | 终止请求/错误证据，且没有后续恢复成功 |
| `INTERRUPTED` | 明确 abort/cancel 或 Transcript `turn_aborted` |
| `INCOMPLETE` | 已开始但不存在成功、失败或中断终态 |

普通成功、API 失败、用户中断和异常进程结束均有版本化样本。缺少终态永远不得合成为 `SUCCEEDED`。

可信度：高，`VERSIONED_SAMPLE`。

### 5.6 Hosted tools

通过目标 provider 成功触发 hosted web search 后：

- Transcript 未出现可用的 `web_search_call`。
- OTel 未出现可识别的单次搜索身份、开始/结束或状态生命周期。
- 只能确认精确 Turn 正常完成，不能确认每次搜索的耗时和结果状态。

结论不是“hosted web search 不存在”，而是“Codex 0.154.0 的当前双源证据不足以交付 hosted tool 级分析”。V1.0 只保留 Turn 级影响和最终可见内容；完整生命周期进入 V1.1 TODO。

可信度：高，`VERSIONED_SAMPLE + 用户确认`。

### 5.7 Metrics

官方匿名 `Metrics` catalog 与可配置 OTel export 是不同契约。正确规则是：

- 匿名目录中的名称本身不能证明本地 OTLP 可得。
- 目标版本真实 OTLP 样本可以证明该版本实际导出了同名指标。
- 2026-09-21 样本实际包含 `codex.turn.ttft.duration_ms`、`codex.turn.e2e_duration_ms`、`codex.turn.tool.call`、`codex.tool.call`、`codex.tool.call.duration_ms` 和 `codex.hooks.run` 等名称。
- 这些 Metric 仍只用于聚合趋势；单次 Trace 使用 OTel logs/traces 和 TranscriptItem。
- 单次 Turn TTFT 可使用带 Turn trace context 的 `codex.turn_ttft` 结构化事件及 `ttft_ms`，不能由聚合 TTFT Metric 反推。

可信度：高，`OFFICIAL + VERSIONED_SAMPLE`，但能力限定为聚合统计。

### 5.8 缺源降级

接收器、投递和业务数据覆盖必须分别表示：

- 接收器：`LISTENING/UNAVAILABLE`。
- 已到达请求投递：`IDLE/READY/DEGRADED/FAILED`；零请求成功率为 `null`。
- 数据覆盖：接收端只有零请求时为 `UNKNOWN`，不得把监听成功或 100% 已到达请求成功率解释为覆盖完整。

双源组合规则：

| OTel Turn | Transcript | 正式 Trace | 性能 | 内容 |
| --- | --- | --- | --- | --- |
| 缺失 | 已发现 | 不创建 | `UNAVAILABLE` | 仅检查，`UNMATCHED` |
| 存在 | 缺失 | 创建 | `AVAILABLE` | `MISSING` |
| 存在 | 延迟 | 创建 | `AVAILABLE` | `PENDING`，后到后重算 |
| 存在 | 身份相同 | 创建 | `AVAILABLE` | `AVAILABLE/EXACT` |
| 存在 | 身份冲突 | 创建 | `AVAILABLE` | `CONFLICT/UNMATCHED` |

可信度：高，`OFFICIAL + SYNTHETIC_FIXTURE + 自动测试`。

## 6. 总体方案对比与选型

### 6.1 候选方案

| 维度 | A. Hook + OTel + Transcript | B. OTel + Transcript | C. Hook + Transcript |
| --- | --- | --- | --- |
| 核心需求匹配 | 覆盖较多，但形成重复事实 | 满足 V1.0 核心执行、性能和内容需求 | 缺少可靠 API、TTFT、传输和 Span 链 |
| 契约稳定性 | Hook、OTel、Transcript 三套契约 | 两套契约；版本适配边界明确 | Hook 和 Transcript 两套契约，但性能语义不足 |
| 关联复杂度 | 两组跨源关联和三方冲突裁决 | Session/Turn/本地 Tool 可使用公共身份 | 需要用 Hook 承担其不能表达的性能语义 |
| 运维成本 | Hook 信任、forwarder、OTLP、Transcript 全部维护 | OTLP + Transcript，链路最少 | Hook 信任和 forwarder 仍不可缺少 |
| 性能能力 | 完整，但 Hook 对性能没有新增权威价值 | OTel 直接拥有 Trace/Span 与耗时 | 无可靠 API/TTFT/父子 Span |
| 安全与隐私 | 三套输入扩大采集与脱敏面 | 两套来源，职责清楚 | 内容与 Hook 仍需两套治理 |
| 测试性 | 状态组合和冲突矩阵最大 | 版本契约、双源组合可控 | 无法测试不存在的精确性能事实 |
| 迁移/回滚 | 表面改动少，长期迁移成本最高 | 需要迁移现有 Hook-first 实现；可保留历史实现回滚 | 保留较多旧实现，但无法满足产品目标 |
| Hosted tools | Hook 仍不能补足当前缺口 | 当前版本降级并推迟到 V1.1 | Hook 仍不能补足当前缺口 |

### 6.2 采用方案

采用方案 B：**OTel + Transcript、OTel-first**。

选择逻辑：

1. OTel 是 API、TTFT、传输、Trace/Span 父子关系和精确性能的唯一可靠来源；移除 OTel 会失去产品核心价值。
2. Transcript 是可见内容、工具参数/结果、命令退出状态、历史补扫和原始证据的唯一完整来源；OTel 不能替代正文。
3. 两者已经通过版本化样本证明 Session、Turn 和本地模型 Tool Call 可以精确关联，不需要 Hook 中转。
4. Hook 无官方事件时间、不重放历史、不覆盖全部 hosted tools；长期保留会增加重复事实、冲突仲裁、安装和运维成本。
5. exporter 缺失时保留 Hook 不能恢复 OTel 独有的 API/TTFT/Span 能力，因此 Hook 不是有效的性能兜底。
6. 当前 hosted tool 缺口已经通过诚实降级和版本范围裁剪处理，不构成保留 Hook 的理由。

### 6.3 淘汰方案

- 不选择 A：短期可复用更多 Hook-first 代码，但长期复杂度、数据冲突和运维成本最高；已有代码量不是架构选型依据。
- 不选择 C：无法满足核心性能分析目标，且会迫使产品用估算值冒充不可获得的精确事实。

### 6.4 适用前提

- 正式 Trace 必须存在可识别的 OTel Session/Turn。
- Codex 版本升级时必须重新运行版本契约测试；未经验证的新版本不得沿用 Tool `EXACT`。
- Transcript 路径、`session_meta` 和 Session/Turn 身份必须通过校验后才能挂接内容。
- 关联冲突不得静默修复；多个候选必须保持 `UNMATCHED`。
- 原始 OTel 和 Transcript 必须留在本地受控目录，不进入公开仓库。

## 7. 关键领域与数据所有权

| 事实 | 权威来源 | 关键规则 |
| --- | --- | --- |
| Session/Turn 执行存在 | OTel | Transcript 不得独立创建正式 Execution/Trace |
| Session/Turn 跨源身份 | OTel + Transcript 共同校验 | 值相同才为 `EXACT`，冲突不合并 |
| API、流、Trace/Span、事件时间与性能 | OTel | Transcript 时间戳不得覆盖 OTel |
| 用户/模型可见内容与原始 JSONL | Transcript | OTel 摘要不得覆盖 Transcript 原文 |
| 本地模型 Tool Call 身份 | Transcript Call ID，与 OTel 共同验证 | 0.154.0 已验证可 `EXACT`；其他版本重新验证 |
| Command Execution 身份与结果 | Transcript | `status/exit_code` 拥有命令结果；缺失为 `UNKNOWN` |
| 并行命令层级 | Transcript 生产者结构 | 一个模型 Tool Call 下多个子执行，不扁平化 |
| Hosted tool 生命周期 | V1.0 不支持 | 只保留 Turn 级影响和最终可见内容 |
| 聚合趋势 | OTel Metric | 不参与单次事件或 Tool 重建 |
