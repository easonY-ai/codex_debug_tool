# 产品需求

## 背景

Codex 执行复杂任务时可能长时间停留在模型请求、首 Token 等待、工具审批、工具执行或其他不可见阶段。现有界面难以回答“慢在哪里”和“为什么慢”。本项目提供本地可视化分析，将 Agent 行为与运行时性能放在同一时间坐标下展示。

## 产品目标

- 还原从用户输入到最终输出的 Agent 行为过程。
- 展示模型请求、TTFT、推理、工具和可验证等待阶段的耗时；审批等待仅在来源提供可验证起止证据时统计。
- 解释单次执行的时间去向，并从多轮统计中识别造成慢和抖动的异常耗时来源。
- 支持历史会话回溯和新会话实时观察。
- 对数据精度和关联可信度保持诚实，不把推测关系展示成精确调用链。

## 目标用户与场景

目标用户是使用本机 Codex Desktop、CLI 或 IDE 的开发者。

主要场景：

- 某个用户问题迟迟没有输出，判断是在等待模型请求、执行工具还是处于未归因区间；有证据时同时展示审批决策。
- 按会话和用户问题检索执行记录，比较不同时间范围或客户端来源的总耗时和 TTFT。
- 查看工具是否串行执行、并行执行、失败或重试。
- 观察上下文和 Token 增长是否伴随延迟上升。
- 回看由 OTel 建立执行骨架、由 Transcript 补齐内容的会话；没有 OTel 时仍可检查 Transcript 原始记录和内容，但不得伪造正式性能 Trace。

## 功能需求

### V1.0 数据源范围

- V1.0 只使用 OTel + Transcript：OTel 提供官方定义的核心行为遥测和性能事实，Transcript 提供可见内容与原始记录。
- Hook 不属于 V1.0 安装、采集、完整度或 Trace 数据源，也不作为 exporter 缺失时的兜底。
- V1.0 按产品分析语义验收，不承诺逐事件、逐字段复刻 Hook API。无法从 OTel/Transcript 取得等价证据的 Hook 特有边界显示为不支持或无证据，不得推测补齐。
- OTel metrics 只用于聚合趋势；单次 Turn、模型请求和工具调用必须使用 OTel logs/traces 与 TranscriptItem，不得从 Metric 反推。
- 官方页面中默认发送给 OpenAI 的匿名 `Metrics` catalog 与可配置的 OTel export 相互独立；目录本身不能证明某项指标会进入本地 OTLP。目标 Codex 版本的真实 OTLP 样本可以把实际收到的指标纳入 `VERSIONED_SAMPLE` 覆盖，但指标仍只用于聚合趋势，不能据此重建单次 Turn、模型请求或工具调用。
- V1.0 不承诺 hosted tool 级身份、状态和耗时，只保留其对 Turn 的可观察影响及最终可见内容。完整 hosted tool 生命周期明确登记为 V1.1 TODO，进入 V1.1 前必须重新验证届时目标 Codex 版本的 OTel/Transcript 契约。
- 一个模型 `custom_tool_call` 包含多个 `CommandExecution` 时，产品保留“一个模型 Tool Call + 多个命令子执行”的父子结构。模型 Tool Call 按模型 Call ID 计数，命令子执行按自身身份计数；并行子执行分别展示状态和时间区间，父 Tool Call 耗时使用父 Span 或整体区间，不对子执行耗时求和。
- V1.0 只展示 OTel 已证明的工具批准/拒绝决策及决策来源，不承诺审批等待起点、持续时间或工具级稳定关联。审批等待耗时显示未知，对应未覆盖区间计入“未归因”，不生成“审批等待过长”诊断。完整审批等待分析登记为 V1.1 TODO。

### 核心概念

- 会话：一次完整的 Codex conversation，由 `session_id` 唯一标识，可以包含多个执行轮次。
- 执行轮次：一次“用户问题到 Codex 最终回复”的执行过程，由 `(session_id, turn_id)` 全局唯一标识；`turn_id` 只要求在所属 Session 内唯一。执行轮次是主列表的统计对象。
- 用户问题：执行轮次的入口文本，也是列表中用于识别轮次的主要内容。
- 模型请求：一个执行轮次内实际发出的单次模型 API 请求；一个轮次可以包含多次模型请求。
- 工作目录和模型属于详情原始字段，不作为首版主要搜索和筛选条件。

### 分析总览

- 主列表展示执行轮次，同时展示所属会话 ID、会话标题、用户问题、来源、状态、总耗时、请求 TTFT、诊断摘要和数据完整度。
- 将会话 ID、会话标题和用户问题拆成独立搜索项，支持按时间、客户端来源和执行状态筛选。
- 展示执行轮次数、总耗时、模型请求 TTFT、工具调用耗时和失败率，以及相应的 P50、P95、P99、最大值和趋势。
- 每个指标在悬浮时必须展示统计对象、计算方式、分子与分母、有效样本数、排除项和数据来源。
- 总览 TTFT 统计筛选范围内所有成功获得首个可见文本增量的模型请求；一个轮次可以贡献多个样本，失败、取消或无首个文本增量的请求不进入分母。
- 模型请求耗时采用客户端观测的端到端口径，不推测拆分网络、服务端排队和模型处理时间；诊断只能表述为“模型请求链路慢”。
- 使用“异常耗时贡献”识别跨轮次的慢和抖动来源，不使用“每轮原始耗时最大类别”作为瓶颈统计。
- 异常基线是当前筛选范围内同类操作的 P50：模型请求按传输方式分组，工具按工具名和规范化操作类型分组，禁止使用可能包含敏感内容的完整命令作为分组键。
- 单次操作只有同时比同类 P50 多至少 1 秒、且相对增幅至少 20% 时才计入异常；异常耗时等于实际耗时减 P50，类别贡献率等于该类别异常耗时总和除以全部类别异常耗时总和。
- 异常贡献展示类别贡献率、异常秒数、受影响轮次数、有效样本数、P50、P95、P99 和最大值。同类有效样本少于 5 个时显示样本不足；没有操作越过门槛时显示没有明显异常，不强行指定瓶颈。
- 明确区分来自精确 OTel 数据和 JSONL 推导的数据。

### Trace 详情

- 执行行为层展示由 OTel 建立的用户入口、轮次生命周期、工具事件、请求与最终状态；Transcript 在同一 Session/Turn 下补齐用户输入、可见 reasoning summary、模型可见输出、工具参数、工具结果和最终输出。
- 性能层展示 API、TTFT、推理、传输、工具执行和重试；审批只展示已验证的决策事实，等待耗时在 V1.0 显示未知。
- 两层共享时间轴，并支持缩放、平移、时间游标和并行泳道。
- Trace 时间轴采用二维结构：水平轴按证据自身时间客观放置全部可归属当前 Turn 的 Span；左侧纵轴逐行列出全部已观察的 Turn 操作节点，包括 Turn Event、模型 Tool Call，以及与执行操作关联的内容节点。每个节点和 Span 都可打开完整来源、身份、状态、时间和关联证据；密集信息在检查器中查看，不用截断的时间条代替完整证据。
- 有操作节点但无可关联 Span 时，该操作行保留，时间轨道不伪造 Span；有 Span 但无法核验其对应操作节点时，每个未关联 Span 保留独立行，左侧标为“未知操作”。OTel 的 Span 身份、父子关系与起止时间保持原样，不能为了填满行而按最近时间强行关联。
- 支持调用关系、阻塞关系、节点详情、原始事件和数据来源检查。内部可以使用关键路径算法去重并行区间，但不把“关键路径构成”作为面向用户的独立指标。
- 时间轴附近展示紧凑的本轮耗时摘要，包括模型请求、工具执行、本地处理和未归因；审批等待作为独立状态显示但不在缺少起止证据时形成耗时分类，其未覆盖区间计入未归因。所有耗时类别之和必须等于轮次总耗时，并行区间不能重复累计。
- 点击执行节点后必须展示 OTel 原始记录、Transcript 内容补齐状态、已有输入/输出和完整 JSONL 原文；缺少内容时明确显示等待补齐或尚未生成。
- OTel 节点不伪造输入和输出；存在关联时可以跳转到对应 Transcript 内容节点并查看两侧证据。
- 展示节点耗时、状态、Token、工作目录、模型、数据来源和关联可信度，其中工作目录和模型仅在详情或原始字段中出现。
- 单轮数据完整度由 OTel Session/Turn 生命周期覆盖率、OTel 工具/请求事件覆盖率、Transcript 内容补齐率和 OTel 性能 Span 覆盖率四项等权计算；关联可信度单独展示，不计入完整度。没有 OTel Session/Turn 骨架时不计算正式分析完整度。

### 实时会话

- 展示当前正在执行和刚完成的轮次，以及所属会话、最新事件时间、当前阶段和已运行时长。
- 支持选中轮次查看最新事件流、阶段进度和实时性能摘要。
- 最新事件中的每个 OTel 执行节点均可点击，并使用与 Trace 详情一致的检查器分别展示执行/性能证据和 Transcript 内容补齐。
- 运行中的内容必须明确标记“生成中”或“尚未生成”，不能伪造完整结果。

### 自动诊断

首版自动诊断完全使用确定性规则引擎，不调用模型。规则基于阻塞关系、绝对阈值、当前范围分位数、失败、重试和数据缺失；结论按对本轮完成时间的影响排序。未来即使引入模型，也只能用于解释已有证据，不能替代规则评分或生成无证据结论。

至少识别以下问题：

- TTFT 过长。
- 模型或 API 请求耗时过长。
- API 重试或传输回退。
- V1.0 不诊断审批等待过长；只有批准/拒绝决策事实，没有等待时长结论。
- 工具执行过长、失败或重试。
- 上下文或 Token 持续膨胀。
- 存在较长的未归因等待。

诊断结论必须包含命中规则、相应事件或时间区间、影响时长或占比、数据来源和可信度。没有足够证据时显示数据缺失，不生成确定性结论。

### 采集状态

- 展示 OTel 接收进度，以及 Transcript 路径校验、`session_meta` 会话身份和内容补齐进度。
- 展示 OTLP logs、metrics、traces 接收状态。
- “采集正常”必须同时满足：OTLP 接口监听成功且最近窗口失败率低于阈值，Transcript 增量读取任务没有持续积压，接收队列没有持续积压，MySQL 可写且最近事务成功。每项必须展示实际值、阈值和最近判定时间。
- OTLP/HTTP 接收器按 logs、traces、metrics 展示接收数量、最近接收时间、平均处理耗时、P99、最大处理耗时和失败次数。处理耗时从收到请求开始，到完成解码、校验并成功加入写入队列；失败次数统计返回非 2xx 的接收请求，不代表模型请求失败。
- OTLP logs、traces、metrics 接口分别展示监听状态、最近成功时间、请求数、成功率、处理耗时 P50/P95/P99/最大值、超时或非 2xx、队列深度与丢弃数量；Transcript 单独展示扫描、增量读取、重复、半行和解析失败数量。
- 严格区分接口可用率、投递成功率和数据覆盖率。成功率以实际到达请求为分母；无请求窗口显示“空闲/覆盖未知”，不能显示 100%。接收端无法观察到的 exporter 未启动、未发送或发送前丢弃，不能计入已知成功率。
- 采集接口处理耗时只表示接收、解码、校验和入队开销，不得作为 OTel 业务 Span 耗时。
- 展示精确、区间、推测和未关联的汇总与分页明细；支持按状态筛选，并展示 Transcript Item、OTel 对象、证据和时间差。
- 分开展示 OTel Session/Turn 骨架覆盖率、OTel→Transcript 内容补齐率和 OTel 性能阶段覆盖率。未关联率是对应补齐率的反向指标，不是性能指标或执行失败率；分母只包含按事件类型理论上需要该补充来源的 OTel 节点。
- 采集状态页支持对已发现 Transcript 手动重试增量解析：从该文件的持久化字节偏移继续读取新增完整行，用于处理文件延迟写入、监听丢事件或短暂解析失败。该操作不重新发现目录且必须幂等；没有 OTel Session/Turn 骨架时，Transcript/TranscriptItem 只进入来源健康、原始记录和内容检查区，不创建正式性能 Trace。
- OTel 配置页面只检测并生成建议，不自动修改用户的 `~/.codex/config.toml`。
- OTel 是核心行为遥测与性能主事实来源。Transcript 采集独立发现并解析允许根目录内的 JSONL：每个 Transcript 以规范 Path 为业务身份，从 `session_meta` 获得 Session ID；每个 TranscriptItem 保存 Path、Session ID 和自身 Turn/Call 候选。Trace 以 OTel `conversation.id`、`turn.id` 建立 Session/Turn 骨架，关联 TranscriptItem 以补齐用户正文、模型可见输出、工具参数/结果和原始记录。OTel 已定义字段以 OTel 为准，内容字段以 Transcript 为准，身份冲突时不合并；两源都没有证据的 Hook 特有边界不进入 V1.0 Trace。
- 展示 OTLP exporter/接收器的监听、最近事件、乱序、重复、延迟和版本支持范围；明确未配置或投递失败时只能检查 Transcript，不能伪造性能数据。
- 单独展示 Transcript 路径健康，至少区分有效、空值、文件缺失、不可读、越出配置根目录或符号链接。该状态影响内容关联能力，但不等同于 OTel 采集失败。
- 对已验证的 Codex JSONL 格式，读取文件第一条完整记录 `session_meta`，从 `$.payload.session_id` 提取文件会话 ID，并与 OTel `conversation.id` 校验。缺少 `session_meta`、字段不可解析或 ID 不一致必须单独告警；不得要求后续每一行都包含 `session_id`。
- UNKNOWN 事件必须原样保存，并按“排序后的叶子 JSONPath + JSON 值类型”组成结构指纹去重展示。列表展示数量、首次/最近出现、来源、合成原始样本和映射状态。
- 用户可以为单个 UNKNOWN 结构指纹配置受限 JSONPath，将外层 `type`、`timestamp`、`payload.type`、`turn_id`、`call_id`、`role` 和正文映射为标准字段，并在保存前查看匹配结果与校验错误。
- 人工映射采用 RFC 9535 JSONPath 的受限子集：根 `$`、对象成员、数组下标和 `[*]`；不支持递归下降、过滤器、函数或脚本。标量字段最多匹配一个值，正文允许按数组顺序合并多个字符串。
- 保存映射后只重新标准化该结构指纹下已保存的 UNKNOWN 记录，不重放 OTel，也不全量重扫 JSONL。
- 配置向导只检测并生成 OTel exporter 建议，不自动修改 `~/.codex/config.toml`。

## 数据边界

- 数据库存储改为本机 MySQL；数据库账号和密码仅通过本地环境变量提供，不写入源码、已跟踪配置或启动命令参数。具体切换范围与门禁见 [MySQL 切换方案](./06-mysql-migration.md)。
- 可以读取用户明确配置的本机 Codex 数据目录。
- 本地数据库可以保存完整用户输入、工具参数、工具结果和模型可见输出。
- 不读取、破解或展示模型未公开的内部思维链。
- 不向外部服务上传采集数据。
- 服务默认只监听 `127.0.0.1`，首版不提供账号、团队共享或远程访问。

## 设计基线与实现边界

- V1.0 的可运行 H5 原型保存在 `prd_and_design/prototype-v1`。同一需求版本的评审迭代直接修改该目录，并用 Git 历史追溯已确认的旧版页面结构、视觉层级和交互行为。
- 原型用于需求还原和评审；真实前端代码位于 `frontend`，后续 API 接入、测试和发布只在正式工程中实施。
- 指标定义、计算口径和数据边界以本 PRD 为准，原型不能替代文字需求。两者冲突时必须先明确并更新需求，不能让实现自行猜测。
- 同一产品版本的原型持续迭代并以 Git 历史追溯；只有新产品版本需要并行维护时才建立新的原型目录。原型不得包含依赖目录、构建产物、本机配置、账号、凭据或真实会话数据。

## 首版不做

- 不修改 Codex 源码以注入公共关联 ID。
- 不承诺 JSONL 和 OTel 的每个事件都能一一对应。
- 不实现云端同步、多用户权限或远程部署。
- 不自动修改用户的 Codex 配置文件。
- 不将聚合 Metric 反推为某一次具体调用。
- 不使用 Transcript 时间戳伪造 OTel API、TTFT、父子 Span 或精确性能缺口。

## 产品验收标准

- 用户能按会话 ID、会话标题或用户问题定位执行轮次并进入详情。
- 用户能在详情中分辨 Agent 行为时间线和 OTel 性能时间线。
- 用户能通过时间轴和本轮耗时摘要判断时间属于模型请求、工具、本地处理还是未归因等待，摘要各项之和等于总耗时；审批决策可见，但没有起止证据时等待耗时必须显示未知且不得从未归因中重复扣除。
- 用户能点击 OTel 执行节点和实时事件，分别查看 OTel 执行/性能原始证据与 Transcript 内容证据。
- 工具稳定约 4 秒、模型通常约 2 秒但少量抖动到 20 秒时，异常耗时贡献必须将模型识别为主要异常来源，而不是把稳定工具误判为瓶颈。
- 所有统计指标均能查看分子、分母、有效样本、排除项和数据来源。
- 用户能理解自动诊断来自确定性规则，并从结论跳转到相应证据。
- 用户能查看数据完整度四项组成，以及采集健康状态的实际值和判定阈值。
- 用户能分页检查四种关联状态，并理解未关联不代表执行失败或性能异常。
- 只有 JSONL 时允许形成 Transcript/TranscriptItem，并用于来源健康、原始记录检查和 UNKNOWN 映射，但不创建正式性能 Trace；已有 OTel 骨架但缺少 Transcript 时，页面仍可展示执行与性能并明确内容缺失。
- 低置信度关联不会被展示为确定关系。
- 同名并行工具无法精确匹配时，页面明确展示歧义。
- 一个模型 Tool Call 内存在多个并行命令时，页面展示一个父调用及其多个子执行，统计分别为父调用 1 次和命令执行 N 次，工具耗时与本轮耗时摘要均不得重复累计并行子区间。
- OTel 记录重复、乱序或延迟到达时，通过协议身份幂等保存并重算 Trace；缺失终态不得合成成功，负耗时不得进入统计。
- 已知格式下，OTel `conversation.id` 与 Transcript Meta `session_id` 一致，且同一 Session 下 OTel `turn.id` 与 TranscriptItem `turn_id` 一致时，Session/Turn 关联为精确；具体工具内容仍由 Trace 逐条关联 TranscriptItem。
- 用户能直接判断 Transcript 是否位于允许根目录、能否解析并与 OTel Session/Turn 关联，并能查看失败原因。
- 用户能按 UNKNOWN 结构指纹去重检查原样记录，使用页面给出的 JSONPath 示例完成映射、预览、校验和单指纹重新标准化。
